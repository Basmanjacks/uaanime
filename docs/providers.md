# uaanime — архітектура джерел

Цей документ фіксує, як uaanime працює з кількома сайтами і кількома відеохостами.

> Стек зафіксовано: Go (ADR-001, 2026-08-31). Головне тут — структура рішень: розділення
> провайдер/екстрактор, власний ID тайтлу, порядок fallback, contract-тести.
Він розширює §3 build-brief і замінює наївне «один провайдер, потім додамо ще».

---

## 1. Дві незалежні осі

Найважливіше рішення в проєкті, і воно неочевидне:

**Provider** — сайт-каталог. Знає, які є тайтли, серії, студії озвучення.
**Extractor** — відеохост. Знає, як з посилання-плеєра дістати придатний до відтворення потік.

Українські аніме-сайти майже не хостять відео самі — вони вбудовують один і той самий невеликий
набір плеєрів. Тому:

```
AniTube ─┐
AnimeUA ─┼─> ashdi / tortuga / moon / …
AniHub  ─┘
```

Наслідок, заради якого це і робиться: **другий провайдер коштує дешево**, бо екстрактори вже
написані. Додати сайт — це лише розбір HTML. І навпаки: коли ламається один відеохост, страждають
усі провайдери одразу, тому екстрактори мають найвищий пріоритет за якістю і тестами.

Ніколи не змішуй ці шари. Провайдер повертає *посилання на плеєр*, а не на відео.

## 2. Інтерфейси

```go
type Provider interface {
    ID() string          // "anitube" — стабільний, потрапляє в дані користувача
    Name() string        // "AniTube" — показуємо як є, не перекладаємо
    Caps() Caps

    Search(ctx context.Context, q string, page int) (Page, error)
    Catalog(ctx context.Context, kind CatalogKind) ([]TitleCard, error) // лише якщо Caps.Catalog
    Episodes(ctx context.Context, ref TitleRef) ([]Episode, error)
    Sources(ctx context.Context, ref TitleRef, episode int) ([]Source, error)
}

type Page struct {                    // сторінка результатів пошуку
    Titles  []TitleCard
    HasMore bool                      // сторінка повна — є сенс просити наступну
}

type Source struct {                  // те, що дав сайт
    Studio  string                    // "FanVoxUA" — оригінальний рядок
    Kind    Kind                      // dub | voiceover | sub | multi
    Host    string                    // "ashdi"
    Embed   string                    // URL плеєра
    Referer string                    // сторінка, з якої його взяли
}

type Extractor interface {
    ID() string
    Handles(embed string) bool
    Extract(ctx context.Context, src Source) ([]Stream, error)
}

type Stream struct {                  // дані для зовнішнього плеєра
    URL     string
    Quality int                       // 1080, 720, 0 = невідомо
    Kind    StreamKind                // hls | progressive
    Headers map[string]string         // Referer, User-Agent — доносимо до плеєра
}
```

`Caps` дозволяє інтерфейсу деградувати без `if provider == "anitube"`:

```go
type Caps struct {
    Search, Catalog, Updates, Ongoing, Descriptions, Subtitles bool
}
```

Перевірка на код провайдера будь-де поза `internal/provider` — архітектурний баг.

### Картка тайтлу і добірки

`TitleCard` вбудовує `TitleRef` — це вся його ідентичність. Решта полів (рік, рейтинг,
кількість серій, жанри, студії, наявність дубляжу й сабів) — **метадані виключно для
відображення**: вони живуть рівно стільки, скільки відкритий список, і ніколи не
потрапляють у `library.json`. Причина та сама, що й з ідентичністю тайтлу: сайт міняє
рейтинг щодня, а прогрес користувача не має від цього залежати. У сховищі — локальний ID
і `TitleRef`; усе інше перечитується з провайдера.

`CatalogKind` має два значення — `top-season` і `fresh`. Окремих URL для них сайт не
зобов'язаний мати: в AniTube обидві добірки розбираються з головної сторінки, різними
парсерами блоків. Каталог — це вітрина, тому він обмежений (≤ 20 карток) і не пагінується;
гортання списків — робота пошуку.

## 3. Ідентичність тайтлу — найскладніше

Одне аніме живе на трьох сайтах під трьома слагами. Якщо прогрес прив'язати до слага, то смерть
AniTube = втрата всієї історії користувача. Це неприйнятно.

```go
type LocalTitle struct {
    ID      string      // стабільний локальний ID, наш, назавжди (unix-ms + random hex, ADR-001)
    Canon   Canonical   // нормалізована назва, рік, тип
    Sources []TitleRef  // по одному на провайдера
}

type TitleRef struct {
    Provider string
    Slug     string
    URL      string
}
```

**Прогрес, історія і список перегляду зберігаються за `LocalTitle.ID` і номером серії. Ніколи за
слагом провайдера.** Провайдери — це змінні шляхи до того самого тайтлу.

Злиття: нормалізуємо назву (нижній регістр, прибрана пунктуація, латиниця↔кирилиця через
транслітерацію), порівнюємо з роком ±1 і типом. Вище порогу — зливаємо, нижче — окремі записи.

Автоматика помилятиметься. Тому потрібні дві ручні команди-запобіжники:

```
uaanime link <title-id> <provider>:<slug>    # приєднати джерело вручну
uaanime unlink <title-id> <provider>          # відчепити помилково злите
```

Не намагайся зробити матчинг ідеальним. Зроби його виправним.

---

## 4. Нумерація серій

Сайти рахують по-різному: рекапи, спешли, розділені сезони. Тому:

- `Episode.Number` — нормалізований наскрізний номер, наш;
- `providerEpisodeKey` — те, чим серію називає конкретний сайт, зберігається поруч;
- якщо у провайдерів розбіжність, довіряємо тому, у якого більше серій, а решту мапимо зі зсувом;
- користувач бачить лише наш номер.

---

## 5. Пошук по кількох джерелах

Паралельні запити до всіх увімкнених провайдерів, дедлайн ~2 с на кожного. Провайдер, який не
встиг, просто не потрапляє в результати — пошук не чекає найповільнішого.

Результати **зливаються в один рядок на тайтл**. Користувач не має бачити «Фрірен» тричі.
Під злитим рядком — об'єднаний набір релізів з усіх сайтів.

Це і є головна перевага uaanime над одноджерельними клієнтами: не «резервна копія на випадок збою»,
а **більше українських озвучок в одному місці**. FanVoxUA на одному сайті, інша студія на другому —
користувач обирає з повного списку, не знаючи, звідки що.

---

## 6. Порядок провайдерів і здоров'я

- користувацький пріоритет у конфізі (`providers: [anitube, animeua, …]`);
- у межах сесії провайдер, що впав двічі поспіль, опускається вниз до кінця сесії;
- це стан у пам'яті, не на диску — вранці сайт може працювати;
- `uaanime doctor` показує кожного провайдера і час останньої успішної відповіді.

---

## 7. Ланцюжок fallback при відтворенні

Порядок жорсткий, перший успіх перемагає:

1. закріплена студія → поточний провайдер → найкращий доступний хост
2. та сама студія → **інший хост**
3. та сама студія → **інший провайдер**
4. інше **українське озвучення** (будь-який провайдер)
5. українські **субтитри**

Кроки 2–3 — це те, заради чого існує вся ця архітектура. Користувач бачить лише
`Джерело недоступне, пробую інше…` і за секунду отримує відео.

Перехід на крок 5, коли на кроці 4 ще є кандидати, — продуктовий баг, а не оптимізація.

## 8. Contract-тести

Один набір тестів, обов'язковий для кожного провайдера:

```go
func TestContract(t *testing.T) {
    providertest.Run(t, fixtureClient(), providertest.Cases{
        SearchQuery:   "фрірен",
        PagedQuery:    "аніме",                                                  // ≥2 сторінки
        Catalogs:      []provider.CatalogKind{provider.CatalogTopSeason, provider.CatalogFresh},
        MultiStudio:   CanonicalRef("title-multi-studio"),
        SingleRelease: CanonicalRef("title-single-release"),
        Ongoing:       CanonicalRef("title-ongoing"),
        Episode:       1,
    })
}
```

`providertest.Run` перевіряє однакові інваріанти для всіх: пошук повертає непорожній результат зі
слагом; картка несе рік і рейтинг (щонайменше половина результатів); друга сторінка непорожня і не
перетинається з першою за слагом; кожна добірка каталогу непорожня, у межах ліміту і з повними
`TitleRef`; сторінка з кількома студіями дає >1 `Source` з різними `Studio`; жоден `Source` не має
порожнього `Embed`; `Kind` ніколи не вгадується як `sub` за відсутності доказів; помилковий HTML не
викликає паніку.

`PagedQuery` і `Catalogs` необов'язкові — порожнє значення вимикає відповідний підтест, тому
провайдер без таких фікстур усе одно проходить контракт.

Саме це робить додавання провайдера дешевим. Без спільного контракту кожен новий сайт — це новий
набір саморобних тестів різної якості.

## 9. Модуль

Рішення ADR-001: у v1 публічного пакета немає — все живе в `internal/` (зобов'язання
стабільного API без реального споживача не береться; винесення в `pkg/` — механічний
рефакторинг, коли споживач з'явиться).

```
internal/provider/            інтерфейси, моделі; providers по підпакетах
  anitube/
internal/extractor/           екстрактори відеохостів
  ashdi/
internal/providertest/        спільні contract-тести
```

Шар джерел (`internal/provider`, `internal/extractor`, `internal/providertest`) не знає
нічого про TUI, конфіг чи прогрес. Він приймає `context` і повертає дані.
Якщо туди потрапить `lipgloss` — щось пішло не так.

## 10. Чого не робити

**Не робити плагінну систему.** Ні динамічного завантаження, ні `.so`, ні скриптів. Провайдери
компілюються в бінарник. Новий сайт — це PR, а не рантайм-механізм.

**Не робити провайдерів на YAML.** «Опишемо селектори в конфізі, і сайти додаватимуться без коду» —
приваблива ідея, яка щоразу перетворюється на власну недомову з умовами, циклами і нульовою
можливістю дебагу. Go-код із фікстурами читається і лагодиться, YAML-DSL — ні.

**Не робити спільний кеш між провайдерами за назвою.** Кеш ключується `(provider, slug)`,
інакше зміна на одному сайті отруює дані з іншого.

**Не додавати провайдера без фікстур.** Провайдер без contract-тестів зламається тихо і невідомо коли.

---

## 11. Чекліст додавання сайту

1. `internal/provider/<name>/`, реалізувати `Provider`
2. чесно заповнити `Caps` — краще `false`, ніж напівробоча функція
3. зберегти чотири канонічні фікстури
4. підключити `providertest.Run`
5. перевірити, чи потрібен новий екстрактор, чи вистачає наявних
6. зареєструвати в реєстрі, додати в дефолтний порядок **останнім**
7. `uaanime doctor` показує новий провайдер

Якщо на кроці 1–6 довелося змінити щось поза `internal/provider/`, `internal/extractor/`
чи `internal/providertest/` — зупинись. Це протікає абстракція,
і полагодити її зараз дешевше, ніж після другого провайдера.

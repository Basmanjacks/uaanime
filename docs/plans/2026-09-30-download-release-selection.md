# Вибір релізу для завантаження та відтворення локальних файлів

Дата: 2026-09-30. Статус: реалізовано й перевірено.

## Мета

Дозволити завантажувати серію в обраній студії й типі перекладу незалежно від
переваги перегляду. Відтворювати локальний файл тільки тоді, коли він відповідає
обраному релізу; інакше шукати цей реліз онлайн. Підтримати кілька релізів і
якостей однієї серії в інтерфейсі та черзі.

Реліз — чинний `provider.Release{Studio, Kind}`. `dub`, `voiceover`, `sub` і
`multi` залишаються різними типами. Якість визначає варіант файла всередині
релізу, а не вибір студії або типу.

## Результати перевірки

Перевірено поточну версію після `3629bfc` (завантаження й офлайн-відтворення).
Сценарії запускалися через тимчасовий Go overlay поза репозиторієм: справжні
Engine/Model/Manager, тестові провайдери й екстрактори, тимчасова файлова система.
Продуктовий код та користувацькі дані не змінювалися.

| Сценарій | Поточний результат |
| --- | --- |
| На диску A/dub, обрано B/dub, B доступна онлайн | Віддається A/dub; 0 викликів провайдера |
| На диску A/dub, обрано A/sub, A/sub доступна онлайн | Віддається A/dub; 0 викликів провайдера |
| На диску A, глобальна улюблена студія B доступна онлайн | Віддається A; 0 викликів провайдера |
| Файл без метаданих релізу, обрано B/sub | Віддається невідомий локальний файл; 0 викликів провайдера |
| Натиснуто D, за тайтлом закріплено FANVOXUA/dub | Відразу відкривається якість FANVOXUA без вибору релізу |
| Збережено FANVOXUA/dub/720p, потрібні Glass Moon/sub | D каже, що серія вже завантажена |
| Після створення завдання змінено пін перегляду | Чинне замикання тримає старий пін; повторне створення для retry бере новий |
| Збережено два релізи: dub/720p і sub/1080p | Один рядок із 1080p; Enter може віддати інший файл, dub/720p |
| У чергу додано FANVOXUA/dub/720p та Glass Moon/sub/1080p тієї самої серії | Повертається один ID; у черзі одне завдання |
| Студії `Team/A` і `Team:A`, решта параметрів однакові | `Filename` повертає однакове ім'я для різних релізів |

Додатково відтворено проблему ключа черги та колізії імен: дедуплікація враховує
лише provider/slug/серію; різні назви студій можуть давати однакове ім'я файла
після санітизації, наприклад `Team/A` і `Team:A`.

Причини:

- `internal/playback/playback.go:285`: `ResolveWith` повертає локальний результат
  до отримання онлайн-джерел.
- `internal/playback/local.go:56`: `library.Pick` бачить тільки локальні релізи
  і застосовує fallback до іншого файла. Невідомий реліз теж повертається.
- `internal/ui/screen_downloads.go:155`: будь-який файл серії блокує D.
- `internal/ui/screen_downloads.go:268`: завдання повторно знімає переваги
  перегляду; конкретний реліз із попереднього екрана не передається.
- `internal/download/manager.go:63`: ключ завдання не містить релізу та якості.
- `internal/ui/screen_downloads.go:395`: локальні варіанти згортаються до одного
  рядка; `playSaved` ігнорує шлях у payload і заново обирає за перевагами.

Зберігання вже має потрібну основу: ім'я файла містить студію, тип і якість,
`Sidecar` містить ідентичність тайтлу, серію та реліз, `SavedTitle.Files` зберігає
всі варіанти серії. Нова база даних або міграція формату sidecar не потрібні.

## Рекомендована поведінка

### Завантаження

1. D відкриває вибір релізу поточної серії. Поточна перевага перегляду визначає
   початковий курсор, але користувач може обрати іншу пару студія/тип.
2. Якщо доступний лише один реліз, можна відразу перейти до його якостей.
3. Enter на релізі відкриває доступні якості саме цього релізу. Enter на якості
   ставить конкретний варіант у чергу. Esc на якостях повертає до релізів, Esc
   на релізах — до серій; після постановки повертаємося до серій.
4. Завантаження не змінює StudioPin/KindPin, watchlist або прогрес перегляду.
5. Варіант, який уже є на диску або в черзі, позначається як наявний.
   Інший реліз або інша якість залишаються доступними. Наявні файли зберігаються.
6. У завданні фіксуються тайтл, серія, реліз, обрана якість і папка. Retry
   повторює ці значення, навіть якщо переваги перегляду вже змінилися.
   Явно обрана числова якість має точно збігатися на старті та retry; якщо
   вона зникла, завдання завершується помилкою без підміни якості. Значення
   0 означає «найвища доступна» й залишається автоматичним при кожному запуску.
7. Потоки отримуються свіжими на старті завдання. Можна переходити між хостами
   одного релізу; недоступність цього релізу завершує завдання зрозумілою
   помилкою, а не завантаженням іншої студії чи субтитрів.

### Відтворення

- Розділити вибір релізу та отримання носія цього релізу. Явний вибір для
  конкретного запуску — точна пара; він відрізняється від автоматичних
  переваг, для яких існує чинний порядок `library.Pick`.
- Для явно обраної пари: точний локальний збіг → найвища локальна якість цієї
  пари без мережі; збігу немає → онлайн-джерела тільки цієї пари. Файл іншої
  студії або іншого типу не є заміною.
- За збереженими перевагами також спершу шукати бажаний реліз на обох носіях.
  Локальний fallback не повинен випереджати бажаний онлайн-реліз. Чинний
  автоматичний fallback застосовується після оцінки доступних релізів, із
  наявними попередженнями та забороною тихої заміни озвучення субтитрами.
- Для автоматичного вибору використовувати спільний набір відомих локальних
  та онлайн-релізів. Метадані серій і кеш допомагають сформувати вибір без
  зайвого отримання потоків; метадані не гарантують працездатності хоста.
  Перший вибір не повинен приховувати відомі онлайн-альтернативи лише тому,
  що один локальний файл уже існує.
- Точний локальний реліз має працювати офлайн. Коли потрібного файла немає
  і мережа недоступна, показати помилку та можливість явно вибрати доступний
  локальний реліз; автоматично інший файл не запускати.
- Файл без достовірних Studio/Kind не вважати збігом обраного релізу. У списку
  завантаженого показувати його як невідомий реліз і дозволяти явний запуск.
- У «Завантаженнях» показати окремий рядок для кожного фізичного файла з
  релізом і якістю. Enter відтворює саме цей файл через спільні Begin/Run/Finish.
  Ця дія може свідомо відрізнятися від поточної переваги тайтлу.
- Явний запуск рядка файла застосовується до цієї серії. За наявного піна A
  запуск файла B не переписує пін: наступна серія/автоплей знову використовує
  A. За порожнього піна свідомий запуск відомого файла запам'ятовує точну
  пару Studio/Kind, включно з sub; наступні серії використовують цю пару.
  Невідомий реліз не створює пін. Звичайний автоматичний локальний запуск
  не закріплює реліз лише через наявність файла. Чинне правило wildcard для
  неявного онлайн-вибору субтитрів і для пікера лише із субтитрами зберігається.
  Саме завантаження нічого не закріплює. Прогрес залишається тайтл/серія.

## План реалізації

1. **Зафіксувати регресії.** Перенести діагностичні сценарії у постійні тести
   з очікуваною поведінкою: точний реліз локально/онлайн, вибір при D, інший
   локальний варіант, retry та точний запуск рядка файла. Чинний тест, що
   очікує локальний fallback для відсутнього піна, переписати відповідно до
   нового порядку пошуку. Справжня мережа не потрібна.
2. **Впорядкувати резолюцію.** У `internal/playback` додати явний вибір релізу
   для одного запиту й отримання джерел тільки цього релізу. Повторні спроби
   між хостами зберігаються. Переробити локальний підбір у точний пошук;
   узгодити автоматичний вибір і список доступних релізів. Використати
   `provider.Release` і чинний `library.Pick`; правила пріоритетів не дублювати.
3. **Закріпити варіант у черзі.** `Job` і `Progress` мають нести конкретний
   реліз. Єдиний типізований ключ дедуплікації: provider/slug/серія/студія/тип/
   обрана якість. UI тримає завдання за ID, а бейдж серії агрегує їх окремо.
   Retry відновлює початкове завдання; обрана якість зберігається окремо від
   фактичної якості у прогресі, зокрема для CLI-запиту «найвища». Зберегти
   послідовне виконання та локи.
   Адаптувати CLI до цього контракту: автоматично обрану пару фіксувати перед
   виконанням; додавання нових CLI-прапорців не входить у цей план.
4. **Додати вибір при D.** Перевикористати список релізів, оформивши явний
   контекст дії «перегляд/завантаження». Розділити наслідки Enter: закріплення
   для перегляду або підготовка якостей для завантаження. Прибрати блокування
   за самим номером серії; передати обрану пару від пікера до плану й завдання.
   Стан запиту очищається при виході; застарілі async-відповіді відхиляються.
5. **Показувати локальні варіанти чесно.** У списку файлів показати студію,
   тип, якість і розмір; загальний розмір тайтлу рахувати за всіма файлами.
   Бейдж «на диску» для серії не має обіцяти, що обраний реліз локальний,
   коли локально є лише інший. Перед явним запуском повторно перевірити файл.
   При колізії санітизованих імен перевіряти sidecar; для різних варіантів
   додати стабільний суфікс лише за потреби. Невідомий існуючий файл не
   приписувати новому релізу автоматично. Старі файли продовжують читатися.
6. **Перевірити інтеграцію.** Виконати наведені нижче перевірки, оновити
   README та локалізовані підказки через `internal/i18n`.

## Критерії приймання та перевірки

- На диску A/dub, обрано B/dub або A/sub: відтворюється потрібний онлайн-реліз.
- Точний реліз локально: жодного виклику провайдера/екстрактора; з кількох
  якостей обирається найвища в межах цієї пари.
- Обидва напрями dub/sub, різні студії й глобальні переваги; wildcard старих
  пінів і `multi`; перший перегляд із наявним файлом та онлайн-альтернативами.
- Офлайн, недоступний хост, відсутній реліз і видалений файл мають зрозумілі
  різні результати. Відмова запуску не змінює прогрес.
- Завантаження B під час закріплення A не змінює бібліотеку. Та сама серія
  зберігається у двох студіях, двох типах і двох якостях, з правильними sidecar.
- Дублі тієї самої пари й якості не створюють друге активне завдання; різні
  варіанти мають різні ID. Зміна піна між планом, чергою та retry не змінює
  обраний реліз. Відмова першого хоста не дозволяє перейти на інший реліз.
- Явна числова якість, що зникла між вибором і виконанням/retry, дає помилку;
  якість 0 обирає поточну найвищу. Перевірити виконання після CLI-preflight.
- Явний запуск локального B за наявного піна A зберігає A для наступної серії;
  без піна відомий B створює точний пін, включно з sub. Невідомий файл і
  автоматичний локальний вибір піна не створюють.
- Кожний локальний рядок запускає свій файл; загальний розмір включає всі
  файли. Колізії назв студій не блокують збереження іншого відомого релізу.
- Esc, повернення до серій, повторний D, прострочені відповіді, resume,
  автоплей і переходи з пульта зберігають правильний вибір і життєвий цикл.
- `make test`, `make lint`, `make build`; headless smoke із фікстурами та
  тимчасовими даними; ручний TUI на малому і звичайному терміналі.

На етапі рев'ю пройшли `go test -race` для `internal/playback`, `internal/ui`,
`internal/download`, `internal/library` та `cmd/uaanime`. Діагностичні overlay-
сценарії підтвердили поточну неправильну поведінку, а не виправлення.
Реальний VLC/mpv, інтерактивний TUI та live-сайти на цьому етапі не перевірялися.

## Межі та наслідки

Нові залежності й налаштування не потрібні. Дані бібліотеки та формат sidecar
залишаються сумісними. Назви студій порівнюються за їх чинною ідентичністю;
зіставлення псевдонімів студій між провайдерами — окреме питання.

Різні релізи можуть мати відмінний монтаж або тривалість. Поточна позиція
перегляду належить серії; автоматичне вирівнювання таймкодів або окрема історія
кожної озвучки не входять у це виправлення.

## Рев'ю плану

- Раунд 1, GPT-6.1-Sol / high: два суттєві зауваження, обидва перевірено й
  прийнято. Уточнено точність числової якості та правила піна для явного
  запуску рядка локального файла, додано відповідні критерії приймання.
- Раунд 2, GPT-6.1-Sol / high: APPROVED; суттєвих зауважень не залишилося.

## Перевірка реалізації

- Рев'ю реалізації тим самим GPT-6.1-Sol / high виявило два суттєві випадки:
  мережевий збій після читання кешованих джерел дозволяв інший локальний
  переклад; короткий локальний шлях ігнорував свіжі джерела й покладався на
  прострочені метадані серій. Обидва виправлено й покрито регресіями.
- Повторне рев'ю — без суттєвих зауважень. Повний прогін додатково показав,
  що збій окремого хоста має зберігати чинний онлайн-fallback. Обмеження
  звужено до автоматичного локального fallback після мережевої помилки;
  точний явно обраний реліз залишається точним. Фінальне рев'ю підтвердило
  поведінку, початкові діагностичні сценарії проходять.
- `make test` — усі Go-тести з race detector і 13 тестів веб-пульта пройшли.
  `make lint` — 0 зауважень; `make build` — успішно.
- Зібраний бінарник: search, episodes, resolve, play --dry-run і doctor
  пройшли з фікстурами й тимчасовим каталогом даних.
- Інтерактивний TUI: на 80×24 перевірено D, список студій/типів і Esc;
  на 40×12 через тимчасовий Go overlay з тестовим транспортом пройдено
  D → Glass Moon/sub → 1080p → збереження → список файлів. Збережені
  субтитри не підмінили автоматичну озвучку: показано відповідний бейдж.
  Вихід відновив термінал. Overlay не змінював файли репозиторію.
- Реальне відтворення у VLC/mpv і live-сайти не перевірялися; медіапотоки
  та гравець у наскрізних тестах підставні, дані користувача не змінювалися.

програма для API-сценаріїв використовувала справжні Engine, Manager і плеєри;
